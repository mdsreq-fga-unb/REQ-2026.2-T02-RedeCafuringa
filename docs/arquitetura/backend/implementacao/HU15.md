# HU15 — Cadastrar produto (backend)

> História: [HU15](../../../visao/historias/HU15.md) · RF15 · RN01, RN02, RN09, RN10, RN11 · RNF03, RNF04, RNF07, RNF08, RNF11.
> Controles e riscos: [segurança](../seguranca.md). Contrato: [Referência da API](../../shared/api.md), tag `products`.

## 1. O que foi entregue

O produtor autenticado cadastra um produto com nome, categoria, descrição, preço por
unidade, gramas por unidade e de 1 a 10 fotos. O produto fica vinculado à conta do
token (RN09) e qualquer pessoa consulta a oferta e quem é o responsável (CA08).

| Método e rota | Acesso | Função | Respostas |
|---|---|---|---|
| `POST /api/v1/products` | `PRODUTOR` | Cadastra o produto (multipart; fotos no campo `fotos`) (CA02–CA05, CA07) | **201** · 400 · 401 · 403 · 404 conta inativa · 413 · 415 |
| `GET /api/v1/products?produtor=&categoria=&pagina=&limite=` | público | Catálogo paginado `{ itens, total, pagina, limite }`, do mais novo ao mais antigo (CA01, CA08; base da HU19) | **200** · 400 filtro inválido |
| `GET /api/v1/products/{id}` | público | Dados do produto e do responsável (CA08) | **200** · 404 (inexistente, indisponível, produtor desativado ou id inválido) |
| `GET /api/v1/products/{id}/photos/{photoId}?v=` | público | Uma foto, em WebP | **200** · 304 · 404 |

Versão do contrato nesta branch: **0.6.0** (rotas novas, sem quebra: sobe o *minor*).

### Campos

| Campo | Regra |
|---|---|
| `nome` | Obrigatório, texto simples, até 120 caracteres depois de normalizado |
| `categoria` | `Produtos` ou `Experiência` (as opções do formulário) |
| `descricao` | Obrigatória, texto simples, até 2000 caracteres |
| `precoPorUnidade` | Reais, com ponto, até 2 casas, de 0 a 100000. Zero é aceito (oferta gratuita), como no formulário |
| `gramasPorUnidade` | Maior que zero, até 2 casas, no máximo 1000000 (1 t) |
| `fotos` | De 1 a 10 arquivos PNG, JPEG ou WebP de até 5 MB cada, na ordem da galeria (a primeira é a capa) |
| `Idempotency-Key` (cabeçalho) | Opcional; 8 a 64 letras, números, `-` ou `_` |

Os textos passam pela mesma normalização da HU12 (`normalizeFreeText`: quebras de linha
unificadas, controles e invisíveis removidos, pontas aparadas). Números chegam como texto
no multipart e só são aceitos em notação decimal simples: `1e3`, `0x10`, `-5`, `40,00` e
texto vazio são recusados (com `Number()` puro, `""` viraria 0 e passaria como preço).
Campos fora do contrato (ex.: `produtor`) são recusados com 400, como no resto da API.

### Fotos

Cada foto passa pelo mesmo tratamento da foto de perfil (HU12): formato conferido pelos
bytes, teto de 50 megapixels, regravação em WebP de no máximo 960 px **sem metadados**
(EXIF/GPS, para não revelar a localização da propriedade). As fotos são processadas uma de
cada vez, para limitar memória e CPU. A URL de cada foto leva a versão do conteúdo, então
o navegador guarda a imagem para sempre; responde com `ETag` e `304`.

As mensagens do multer (em inglês) são traduzidas por `PhotoUploadErrorsInterceptor`:
413 vira "Cada foto deve ter no máximo 5 MB" e excesso de arquivos vira "Envie no máximo
10 fotos…", porque o front mostra a orientação do servidor ao produtor (RNF03).

### Galeria de fotos reutilizável

As fotos do produto usam a **galeria genérica** de `backend/src/common/photos/`, pensada
para qualquer entidade com uma ou mais fotos (propriedade, galeria do perfil, eventos…):

| Peça | Função |
|---|---|
| `photo-processing.ts` | Tratamento de toda foto da plataforma (também usado pela foto de perfil da HU12) |
| `photo-gallery.policy.ts` | `PhotoOwnerType` (a quem a galeria pertence) e `PHOTO_GALLERY_POLICIES` (campo, mínimo, máximo, tamanho por foto) |
| `photo.schema.ts` | Coleção `photos`, com `dono { tipo, id }` e `ordem` (0 = capa) |
| `photo-gallery.service.ts` | `prepare` (quantidade + processamento, antes de gravar), `store`, `find`, `removeAll` |
| `photo-gallery-upload.ts` | `@PhotoGalleryUpload(política)`: multer em memória com os limites da política e mensagens em português |

Nova galeria (ex.: fotos da propriedade) = um valor em `PhotoOwnerType`, uma política,
`@PhotoGalleryUpload(...)` na rota e, se aceitar mais que 1 MB, uma linha no Caddyfile.
O teste `caddy-limits.spec.ts` falha se o limite do Caddy não acompanhar a política.

**Por que existe um máximo:** os arquivos ficam em memória durante o envio e o proxy
precisa saber o maior corpo aceitável; sem teto, um envio só derrubaria o servidor.
O teto é por tipo de galeria, num único lugar.

## 3. Dados

Coleção `products`:

| Campo | Tipo | Observação |
|---|---|---|
| `_id` | ObjectId | |
| `produtor` | ObjectId | `users._id`; indexado |
| `nome`, `descricao` | string | |
| `categoria` | string | enum `Produtos` / `Experiência` |
| `precoCentavos` | int | Centavos, para não acumular erro de ponto flutuante; a API expõe reais |
| `gramasPorUnidade` | number | |
| `fotos` | `[{ id, versao }]` | Ordem do envio; aponta para `photos` |
| `disponivel` | bool | Padrão `true` (RN10) |
| `chaveIdempotencia` | string? | Índice único parcial `{ produtor, chaveIdempotencia }` |
| `criadoEm`, `atualizadoEm` | Date | `timestamps` do Mongoose |

Índices do catálogo: `{ disponivel, criadoEm: -1, _id: -1 }` e `{ produtor, disponivel, criadoEm: -1, _id: -1 }`.
A listagem filtra o produtor ativo no próprio banco (`$lookup` em `users`) antes de paginar,
então `total` e páginas sempre batem.

Coleção `photos` (compartilhada por todas as galerias): `{ _id, dono { tipo: 'produto', id }, ordem, dados (WebP), tipo, largura, altura, bytes, versao, criadoEm }`,
com índice `{ dono.tipo, dono.id, ordem }`.
Binários ficam fora de `products` para nenhuma listagem carregá-los por acidente. Cada foto
tem ~50–100 KB; o backup diário já inclui a coleção.

Índices novos são criados pelo `./scripts/dev.sh up` (local) e, em produção, por
`./scripts/dev.sh indexes --prod` depois do deploy.

## 4. Como o front conecta

- `app/src/features/offers/productService.ts` envia `FormData` com os campos acima, o token e o cabeçalho `Idempotency-Key`.
- `ProductRegistrationPage` gera a chave ao abrir e troca a cada edição: repetir sem editar reaproveita a chave (não duplica); editar é outro cadastro.
- As fotos da resposta são caminhos relativos à base da API; o app usa `apiResourceUrl`.
- O front reduz cada foto no aparelho antes de enviar (`prepareProfilePhoto`, da HU12), valida o máximo de 10 fotos e mostra a orientação do servidor em 400/413/415. 404 (conta desativada) tem mensagem própria.
- No modo de demonstração (`VITE_USE_MOCK_AUTH=true`) o cadastro é simulado no navegador.

### Integração com a HU19 (catálogo)

A branch `feat/hu19` lê `GET /products` esperando outro formato (`ApiProduct`). O contrato
oficial é o desta HU (OpenAPI 0.6.0, tipos em `app/src/shared/api/schema.ts`). Ajuste no
`productAdapter.ts` da HU19:

| HU19 (`Product`) | API (`ProductListResponse.itens[]`) |
|---|---|
| lista | `resposta.itens` (paginado; use `pagina`/`limite` ou o padrão de 20) |
| `id` | `id` |
| `name` | `nome` |
| `producerName` | `produtor.nomeIniciativa` (e `produtor.id` para o link do perfil) |
| `price` | `precoPorUnidade` |
| `unit` | `"unidade"` (o preço é sempre por unidade; peso em `gramasPorUnidade`) |
| `image` | `apiResourceUrl(fotos[0])` (a primeira foto é a capa) |
| filtro `disponivel` | já vem filtrado; o campo existe e é sempre `true` nas rotas públicas |

Atenção ao merge: as duas branches criam `app/src/features/offers/productService.ts`.
Juntar num arquivo só, com `registerProduct` (HU15) e `listProducts` (HU19).

## 5. Decisões

| Decisão | Motivo |
|---|---|
| Fotos no MongoDB, como na HU12 | Sem serviço novo nem custo extra; volume pequeno (até 10 × ~100 KB por produto). Se o catálogo crescer muito, trocar por armazenamento de objetos dentro de `PhotoGalleryService`, sem mudar o contrato (as URLs já são opacas) |
| Galeria genérica em `common/photos` | Produto, propriedade e outras entidades com várias fotos reaproveitam armazenamento, tratamento, limites e mensagens; muda só a política |
| Tratamento de imagem único (`processPhoto`) | Mesmo cuidado de privacidade e segurança da HU12, um só lugar para corrigir |
| Envio das fotos junto com o formulário (multipart) | É o contrato que o front já usa. Se surgirem galerias grandes ou conexões muito instáveis, evoluir para envio foto a foto (uma requisição por foto, com retomada) dentro da mesma galeria |
| Preço em centavos | Evita `0.1 + 0.2` no banco; relatórios e somas futuras ficam exatos |
| Nome da iniciativa lido na consulta, não copiado | Reflete alterações de cadastro e não duplica dado pessoal |
| Idempotência por cabeçalho opcional | Padrão de mercado para POST com retry; clientes antigos continuam funcionando |
| `Experiência` (singular) como categoria do produto | É o valor do formulário. Difere de `ProducerCategory` (`Experiências`) do cadastro do produtor, que descreve o produtor, não o item |

## 6. Fora do escopo e pendências

- Editar, excluir e alterar disponibilidade (RF16–RF18): HUs próprias. O schema já tem `disponivel`.
- O catálogo do front desta branch ainda é estático; a tela que consome `GET /products` é da HU19 (ver seção 4).
- Busca por texto no servidor: a HU19 filtra no aparelho por enquanto; com o catálogo grande, acrescentar `busca` à listagem.
- Listar os próprios produtos indisponíveis (gestão do produtor) fica para a HU de disponibilidade (`GET /products/me`).
- Não há limite de produtos por produtor além do rate limit global.
- Restringir a categoria ao tipo de oferta do produtor (`categoriaOfertada`) não foi pedido; avaliar com o PO.
- `gramasPorUnidade` é obrigatório também para `Experiência`, como no formulário atual; avaliar com o PO.
