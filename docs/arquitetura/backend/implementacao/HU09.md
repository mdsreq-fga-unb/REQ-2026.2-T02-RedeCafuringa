# HU09 — Autenticar usuário

> História: [HU09](../../../visao/historias/HU9.md) · RF09 · RN01, RN05 · RNF03, RNF08, RNF10, RNF11.
> Controles e riscos: [segurança](../seguranca.md). Contrato: [Referência da API](../../shared/api.md), tag `auth`.

## 1. O que foi entregue

O usuário cadastrado (consumidor, produtor ou administrador) entra com **e-mail e senha** e recebe um token de acesso. Cada rota da API confere o token e o perfil antes de responder. O CPF e o CNPJ não são credenciais (RN05).

A HU09 foi construída em partes, junto das primeiras histórias de cadastro. Esta página reúne tudo o que a compõe e registra a revisão feita sobre o conjunto.

| Método e rota | Acesso | Função | Respostas |
|---|---|---|---|
| `POST /api/v1/auth/login` | público, limite estrito | Troca e-mail e senha por um JWT (CA02, CA03, CA04) | **200** · 400 corpo inválido (inclui `cpf`) · 401 · 403 conta desativada · 429 |
| `GET /api/v1/auth/me` | qualquer perfil autenticado | Perfil de quem é dono do token (CA05) | **200** · 401 |

Resposta do login: `{ accessToken, tokenType: "Bearer", expiresIn, usuario }`. O `usuario` nunca traz hash de senha e traz o CPF sempre mascarado.

### Regras do login

| Regra | Como é atendida | Por quê |
|---|---|---|
| Credenciais são e-mail e senha | `LoginDto`: `email` e `senha`; qualquer outro campo, como `cpf`, é recusado com 400 | RN05 |
| Mesma resposta para e-mail inexistente e senha errada | 401 `E-mail ou senha inválidos` nos dois casos; para e-mail inexistente a API gasta o mesmo tempo de uma verificação de senha (`verifyDummy`) | Não revelar quais contas existem nem por mensagem, nem por tempo |
| Conta desativada só aparece depois da senha correta | A senha é conferida antes do 403 `Conta desativada` | Quem não sabe a senha não descobre o estado da conta |
| Senha em hash argon2id | `PasswordHasher` | RNF11 |
| Token sem dado pessoal | O JWT carrega só `sub` (id) e `perfil`; nada de CPF, e-mail ou nome | RNF11 |
| Token de 15 minutos, algoritmo fixo | HS256, `JWT_EXPIRES_IN` (padrão 900 s, entre 60 e 86 400); a verificação não aceita `alg: none` nem outro segredo | Reduz a janela de um token roubado |
| Limite de tentativas | Por IP: `AUTH_THROTTLE_LIMIT` (padrão 5) a cada `THROTTLE_TTL` (padrão 60 s); excesso recebe 429 com `Retry-After`. Em produção `TRUST_PROXY=1` faz o limite enxergar o IP real atrás do Caddy | Freia força bruta (RNF08) |
| Credenciais protegidas em trânsito | O Caddy redireciona HTTP para HTTPS e envia HSTS; o login é sempre `POST` com o corpo; o log só registra id, método, URL sem a query e IP, nunca o corpo | CA06, RNF10 |

### Acesso conforme o perfil (CA05)

- `JwtAuthGuard` global: **toda rota exige token**, exceto as marcadas `@Public()` (negação por padrão).
- `RolesGuard` com `@Roles(...)`: cada rota diz quais perfis entram. Não há hierarquia: administrador não herda permissão de produtor.
- Sem token, token malformado, expirado, assinado por outro segredo, `alg: none` ou de conta removida: **401**. Perfil errado: **403**.

### 2.2 Mensagens do login no front (CA04, RNF03)

| Situação | O que a pessoa vê |
|---|---|
| E-mail ou senha errados (401) | `E-mail ou senha inválidos` |
| Conta desativada (403) | `Conta desativada. Procure a administração da Rede Cafuringa.` (tentar de novo não resolve) |
| Excesso de tentativas (429) | `Muitas tentativas de login. Aguarde 2 minutos e tente novamente.` O tempo vem do `Retry-After`; sem ele, "alguns instantes" |
| Falha de rede ou do servidor | `Não foi possível entrar agora. Tente novamente em instantes.` |

### 2.3 Sessão no navegador

- O token e os dados da sessão ficam no `localStorage` (`useDemoSession`). A administração pede novo login a cada abertura do app.
- O JWT dura 15 minutos e **não é renovado**. A interface lê o `exp` do token (só para decidir o que mostrar; quem recusa o token de verdade é o servidor): um token já vencido não abre sessão, e a sessão é encerrada no instante em que o token vence, levando ao login. Sem isso, a pessoa ficava com telas de produtor ou administrador abertas enquanto a API respondia 401.
- Ao abrir o app, `GET /auth/me` confere a sessão; 401 ou 403 encerram a sessão local.

## 3. Revisão feita sobre o que já estava na `dev`

A branch partiu de um estado em que o backend da HU09 já estava completo e testado. A revisão encontrou, e esta entrega corrige, estes pontos:

| Achado | Correção |
|---|---|
| O front mostrava a mesma mensagem genérica para conta desativada (403) e para excesso de tentativas (429). Para conta desativada, "tente novamente" nunca resolve; para o 429, a pessoa não sabia quanto esperar | Mensagem por causa (tabela 2.2) e classes `AccountDisabledError` e `TooManyAttemptsError` |
| A interface continuava "logada" com o token vencido, mostrando áreas que a API já recusava | Encerramento da sessão no vencimento (2.3) |
| `InvalidCredentialsError` ainda dizia "CPF ou senha inválidos", resquício de antes da RN05 | Texto corrigido para "E-mail ou senha inválidos" |
| A redação de logs previa `req.body.password`, mas o campo se chama `senha` (e `novaSenha`, `token` na HU10) | Campos adicionados à lista. É uma segunda barreira: o log já não registra o corpo da requisição |
| O teste E2E se chamava "HU09 — Realizar login para acessar o meu perfil", título que não é o da história | Renomeado para "HU09 — Autenticar usuário" |
| Faltava uma página com a rastreabilidade da HU | Esta página |

## 4. Limites conhecidos e riscos

- **Sem renovação nem revogação de token.** Desativar uma conta bloqueia novos logins e o `/auth/me`, mas um token já emitido segue válido nas demais rotas até vencer (15 min). A HU10 (recuperação de acesso) encerra as sessões anteriores quando a senha é trocada.
- **O limite de tentativas é por IP, não por conta.** Um ataque distribuído contra uma única conta não é freado por ele. Para o volume do MVP é aceitável; se virar problema, somar um limite por conta com bloqueio temporário.
- **Token no `localStorage`.** Qualquer script injetado na página o leria. A mitigação é a CSP do front e o fato de o app nunca inserir HTML não confiável. A alternativa (cookie `HttpOnly`) exigiria CSRF e outra política de CORS e fica como evolução.
- **Sair da conta é local.** `signOut` apaga os dados do navegador; o token em si segue válido até vencer, porque não há lista de revogação.
- **O DoD da HU09 depende da revisão da equipe** e não foi marcado aqui.

## 5. Como testar

```bash
./scripts/dev.sh check                # lint, formato, tipos, build e testes (back e front)
./scripts/dev.sh test backend --e2e   # inclui auth.e2e-spec.ts e rbac.e2e-spec.ts
```

Manual (com `VITE_USE_MOCK_AUTH=false` e a API no ar): entrar com credenciais certas, com senha errada, com e-mail inexistente, com uma conta desativada e com seis tentativas seguidas. Cada caso deve mostrar a mensagem da tabela 2.2.
